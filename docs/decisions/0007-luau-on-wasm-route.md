# ADR-0007: Luau on wasm, the route chosen

- Status: accepted
- Date: 2026-11-25
- Issue: #145

## Context

Risk R5 in [mvp-roadmap.md](../specs/mvp-roadmap.md): Luau is C++, and `wasm32-unknown-unknown` has no C or C++ standard library, so `mlua` with a vendored Luau might not build for the web. Owner decision 3 already fixed the fallback: if no route works, scripts are native-only and `exitium_script` builds for wasm as a cfg-gated stub.

The R5 spike ([luau-wasm-spike.md](../specs/luau-wasm-spike.md), #136) is the evidence. This ADR records the route it chose and turns its conditions into rules that later work must follow. It does not re-run the spike. In short, the spike found:

- `mlua` 0.12.3 with the `luau` feature builds for `wasm32-unknown-unknown` on stable Rust, on Windows and on Ubuntu 24.04, when C and C++ are built by wasi-sdk 34.
- In Chrome 158, mlua's own tests passed. Luau adds about 0.46 MB gzipped to the web build (budget gap: 3 MB). Every speed ratio is under the 2.5x budget (one Lua to Rust call: about 69 ns against 43 ns native).
- The cost is toolchain, not size. The Linux CI image needs the SDK, the loader needs a shim, and the module needs WebAssembly exception handling with `exnref`, which moves the web floor from Chrome 113 to Chrome or Edge 137.
- The 10,000-entity `update` took 2.2 ms (pure) and 2.8 ms (one Rust call per entity) per frame in a micro-benchmark. In a live `requestAnimationFrame` loop in headless Chrome, the version with one Rust call per entity had a median of 3.2 ms (0.8 ms under the 4 ms budget), p99 5.1 ms and a worst frame of 5.7 ms. So the budget holds at the median and not at p99, and it is not settled until it is measured in the real engine.

The owner's roadmap says AD2 records the outcome either way and nothing waits for the owner (ADR-0005 applies as usual: this ADR merges after the AI review).

## Decision

**Luau runs on the web through route A: `mlua` with the `luau` feature, with C and C++ built by wasi-sdk, as the real VM.** Owner decision 3's native-only fallback is not needed. It stays as a verified SDK-free build (the stub) and as the fallback if a tripwire below fires.

### Rules

1. **Feature gate (whole workspace).** The wasm Luau build is behind a Cargo feature `luau` on `exitium_script`, off by default, so `cargo build --workspace --target wasm32-unknown-unknown` builds the SDK-free stub. Resolver 3 unifies features across every selected member, so three rules keep one manifest from turning it on for everyone:
   1. Native always builds Luau. `exitium_script` declares `mlua` under `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`.
   2. The `luau` feature only has an effect on `wasm32`. It adds the optional `mlua` dependency, the allocator and the link setup there. On native it changes nothing.
   3. **No manifest enables `luau`.** That covers `exitium_script`'s own `default`, every `examples/*` crate and the `exitium` facade. The facade and a game crate may **declare** a forwarding feature (`luau = ["exitium_script/luau"]`) that nothing enables by default, because a command-line `--features` needs something to receive it. The web export and the SDK-gated CI step pass it on the command line.
   4. **`exitium_script` is never in `NATIVE_ONLY`.** It builds for `wasm32-unknown-unknown` in both arms (the VM with `luau`, the no-op stub without), so the workspace wasm build keeps covering it and every runtime crate keeps its wasm build.
2. **`mlua` entries.** With the optional entry in `[dependencies]` and the target-scoped one, `features = ["luau"]` goes on **both**. The feature reaches wasm through the entry that wasm sees, which is the optional one.
3. **CI.**
   - `cargo xtask ci wasm` gains a step that builds `exitium_script` with the feature on, by adding `("exitium_script", "luau")` to `FEATURE_CHECKS` in `xtask/src/ci.rs`. The same entry makes clippy and test run the feature natively, where it is a no-op and needs no SDK. **That entry alone only compiles an rlib. It never links**, so it cannot see the link failures the spike found (a missing `_initialize` export, `posix_memalign` undefined, the `build.rs` link libraries unused).
   - So the SDK-gated step also **links**. It builds a small **`bin`** fixture that depends on the `exitium` facade (so the allocator static is linked too) with `luau` on the command line for `wasm32-unknown-unknown`, runs it through `wasm-bindgen` 0.2.130, and asserts, with no browser: (a) `_initialize` is exported, and (b) the imports from the module `wasi_snapshot_preview1` are a **subset** of the eight the shim implements (`environ_get`, `environ_sizes_get`, `clock_time_get`, `fd_close`, `fd_fdstat_get`, `fd_seek`, `fd_write`, `proc_exit`), so a ninth fails the check. Import modules other than `wasi_snapshot_preview1` are ignored: after `wasm-bindgen` the module also imports its own `wbg` glue. A `bin` because shipped games build as executables and the link shape `wasm-ld` sees differs from a `cdylib`, which is all the spike tested. A `cdylib` fixture may sit beside it for the spike's shape. The fixture is a `publish = false` crate that declares the forwarding feature and enables nothing (rule 1.3). `xtask` reads the module's import and export sections itself (std only), or the PR that adds a parser dependency justifies it.
   - The wasm half of these steps needs the SDK. **On GitHub Actions (`GITHUB_ACTIONS` is set) a missing SDK is a hard failure**, so a broken Docker layer cannot pass silently. `GITHUB_ACTIONS` and not `CI`, because an agent harness may set `CI` and a plain `cargo xtask ci all` must not need the SDK in an agent worktree. Locally the steps run only when `WASI_SDK_PATH` is set or the SDK is provisioned, and print a notice when skipped.
   - The steps run only in the Linux Docker job (`ci.yml` `linux`). The Windows runner job stays clippy and test only, because it is the owner's host with no SDK.
   - **No Chrome job runs in CI today**, and the assets spec does not propose one for the MVP. So the allocator's `posix_memalign` and `free` forwarding is checked (a) by a Chrome run recorded in the SP9 PR body (the spike's checks, as a script the PR commits or describes), and (b) by a follow-up issue for a headless Chrome check in CI (owner-pushed `ci.yml` or Dockerfile change if needed). Until (b) lands, a Chrome run in the PR body is the only runtime evidence, and each later PR that touches the allocator, the init path or the loader repeats it.
   - `xtask` provisions the SDK from the pins above into a checksum-verified location. It sets the target-scoped compiler variables (`CC_`, `CXX_`, `AR_`, `CFLAGS_`, `CXXFLAGS_`, `CXXSTDLIB_wasm32_unknown_unknown`) for its child `cargo` only. No `RUSTFLAGS` and no global `LUAU_CXXFLAGS`.
   - The Linux Dockerfile (`ci/runner/linux/Dockerfile`) gains the SDK layer.
4. **Build script.** `exitium_script/build.rs` reads the target from `CARGO_CFG_TARGET_ARCH` and `CARGO_CFG_TARGET_OS` (not `cfg!`, which is the host in a build script), does nothing unless the target is wasm and `CARGO_FEATURE_LUAU` is set, and then links `c++`, `c++abi`, `unwind`, `wasi-emulated-process-clocks` and `c` from the SDK's `eh` and base lib directories, and compiles a 3-line `reactor.c` that exports `_initialize`. It needs `cc` as a build-dependency. The first script-lane PR that adds the wasm VM (SP9's "Luau VM wrapper" issue) creates `build.rs` and `reactor.c`, and `exitium_script` owns both. Intake 2 (#157) only adds the `cc` entry to `[workspace.dependencies]`.
5. **Init and loader.**
   - `_initialize` runs exactly once and first. A Rust once-guard protects it and no Rust allocation happens before it. A second call hangs `init()` (observed). Allocation before it happened to work (observed) and must not be relied on.
   - **The `unsafe` call.** `extern "C" { fn _initialize(); }` and its call are `unsafe`. They live in the same designated `#[allow(unsafe_code)]` module of `exitium_script` as the allocator (rule 6), behind one safe, once-guarded function, with a `// SAFETY:` comment (called once, before any C or C++ code runs).
   - **Who calls it.** Exactly one start function exists in the final module: the game's entry, which is the `bin`'s `main` (`wasm-bindgen` runs an exported `main` as the start function, so no `#[wasm_bindgen(start)]` attribute is needed), and its first statement is that safe function. No library crate may declare a `#[wasm_bindgen(start)]` function, because the order between several start functions is not guaranteed and an allocation in an earlier one is the case this rule forbids. SP9 adds a test that finds a `#[wasm_bindgen(start)]` in a library crate of the workspace. The spike used the attribute on a `cdylib`, so the `bin` shape is covered by the fixture of rule 3.
   - The loader (generated by `exitium export`, and `exitium_platform`'s example loader) must capture `instance.exports.memory` as soon as the instance exists, give it to the WASI shim, and carry an import map for the bare specifier `wasi_snapshot_preview1`.
   - Without a reactor entry point every export after the first hangs, and without `_initialize` Luau traps in `newclasspage`. These are the spike's gaps 1 and 2.
6. **Allocator.**
   - **Why.** The recipe (`mlua`'s `docs/wasm32.md`) forwards Rust's global allocator to wasi-libc's, so Luau's C allocations and Rust's share one heap. The spike followed it and did not test two heaps in one linear memory, so "must share" is the recipe's requirement and not a measured one. Whether the forwarding is needed at all stays open (spike open question 3) until SP9 tests it. Until then the forwarding is the rule. Under `luau` on wasm the `#[global_allocator]` forwards to wasi-libc's `posix_memalign`, `realloc` and `free`. It is **gated on the same feature**: the spike observed the stub failing to link (undefined `posix_memalign`) when the allocator was on for every wasm32 build.
   - **One rule for wasm with `luau`.** The `exitium` facade declares the single `#[global_allocator]`, under `cfg(all(target_arch = "wasm32", feature = "luau"))` only. By default it is `WasiAllocator`. A facade feature `alloc-stats` (declared, off by default, never enabled by a manifest, like `luau`) swaps it for `Counting<WasiAllocator>`, so a game can still read #64's counter. A game or bench binary **must not** declare its own `#[global_allocator]` in that configuration (a second one is a duplicate lang item), so `alloc-stats` is its opt-in there.
   - **Native, and wasm without `luau`.** The facade declares nothing. #64's counter stays opt-in: the game or benchmark binary sets it as `#[global_allocator]`, over `System`. This is the rule in PR #168's ecs-scheduler text and in #64's own acceptance line ("set by the game/benchmark binary, not by the library"), with **one exception**: on wasm with `luau` the facade installs an allocator, because one is required there. Both texts need that exception (follow-up 7).
   - **Why the facade.** A library crate may not normally declare a `#[global_allocator]`, because a final binary has one. The facade is the exception: it is in every game's graph exactly once, so it is the single place that can hold the static and a game cannot forget it. `exitium_script` must not declare it (it can be in a graph without the facade, such as the `FEATURE_CHECKS` rlib build, `-p exitium_script --features luau`, which links nothing), and no other library may.
   - **Gates cannot drift.** The facade's `luau` gate implies `exitium_script/luau` (`luau = ["exitium_script/luau"]`), so facade-on means script-on. For the reverse, `exitium_script` exports a `const LUAU_ON_WASM: bool` and the facade carries `const _: () = assert!(!exitium_script::LUAU_ON_WASM || cfg!(feature = "luau"), "exitium_script/luau is on but the exitium facade's luau feature is off: enable the facade's luau feature (the allocator and init order depend on it)")`, a message that names both features. A build that has Luau on with Rust's default allocator (two heaps, untested) fails to compile.
   - **Unsafe.** The forwarding type, and the `_initialize` call of rule 5, live in one designated `#[allow(unsafe_code)]` module of `exitium_script` (it owns the feature and the link setup), with a `// SAFETY:` comment on each block. The facade's static is safe code. Miri cannot run the wasi-libc FFI, so the wrapper's logic is Miri-tested over an inner `System` allocator. The FFI half is checked by the link assertion (rule 3) and by a Chrome run (rule 3: recorded in the SP9 PR, a CI job as a follow-up). It is not "checked by CI" until that job exists.
   - **Miri.** `cargo xtask ci miri` runs `miri test -p exitium_script` with default features, and native always builds Luau (rule 1.1), so Miri compiles the vendored C++ Luau with a C++ compiler and the tests run longer. SP9's spec says how the Miri run copes (a Miri-only test selection, or a `cfg(miri)` exclusion of the VM tests).
   - **Forwarding.** It forwards `alloc_zeroed` and `realloc` (for alignments up to the malloc alignment) too, because the spike's `alloc`/`dealloc`-only version made `Vec` growth pessimistic. The allocation-heavy benches are re-run after that change.
   - **Existing benches.** The wasi-libc allocator must not regress the existing wasm benches by more than 5% (CLAUDE.md rule 4). Those benches contain no Luau. SP9 runs them with `luau` on and off and records both.
   - **Counting.** #64's counter must wrap any inner allocator (`CountingAllocator<A>`), so the facade can compose `Counting<WasiAllocator>` under `alloc-stats` and a native binary can compose `Counting<System>`. `Counting<A>` forwards `realloc` and `alloc_zeroed` to the inner allocator as well as `alloc` and `dealloc`: the default `realloc` (allocate, copy, free) would undo the forwarding above under `alloc-stats`. See the follow-ups.
7. **Export contract.**
   - Scripts **off**: `exitium export --target web` builds the SDK-free stub. The page has no WASI shim, import map or `exnref` probe, and its floor stays Chrome or Edge 113.
   - Scripts **on**: `exitium export` and `exitium export --check` fail when the SDK is absent, print the fix command, and never fall back to the stub (the scripts would silently do nothing). The page carries the shim, the import map, the memory capture, the start function and the `exnref` probe.
   - A failing `wasm-opt` falls back to the unoptimised module with a warning. It never breaks the export.
8. **Browser floor: Chrome or Edge 137 for a game with scripts. Decided.** `exnref` ships in Chrome and Edge 137, so Chrome and Edge 113 to 136 (WebGPU but no `exnref`) are out for script games. The legacy exception ABI is **not** built: it would double the SDK libraries and add a runtime switch. The page tests the feature, not a version: a `WebAssembly.validate` on a 28-byte module with one `try_table` (opcode `0x1f`), and shows "This game needs a browser with WebAssembly exception handling (Chrome or Edge 137 or later)". The assets spec ([assets-scene-export.md](../specs/assets-scene-export.md), PR #166) keeps 113 as the base web floor and adds exactly this conditional 137 for script games, so this ADR needs no change to it. The probe's negative case (a browser without `exnref`) was not run in the spike, so the export PR must run it. If a later example's players need older Chrome, a new ADR supersedes this rule.
9. **Examples.** No example's scripted part is native-only. `topdown`'s Luau gameplay scripts run on the web, behind the 137 floor. Each example's rules still run in Rust (owner decision 3), so this is a choice and not a dependency: the stub arm stays available.
10. **Budgets.** The roadmap's budgets stay as written and SP9 may only tighten them: web wasm at most 13 MB gzipped with Luau (spike: +0.38 to 0.48 MB) and at most 10 MB without it (the stub export), Luau on wasm at most 2.5x native, a reflected field access at most 200 ns, 10,000 scripted entities at most 4 ms per frame, hot reload of 500 lines at most 50 ms (not measured). SP9's benches run in the real engine on the live loop, report p99, repeat the nine-run method on a quiet machine, and use the Windows "High performance" plan (the spike's E8 numbers ran under "Power saver").

### Tripwires

If any of these fires in SP9 or later, the fix is a new ADR that supersedes this one and flips the wasm arm to the stub (owner decision 3). The stub is kept and built by default for exactly this reason.

1. The full engine module (with `wgpu` and `winit`) fails to instantiate in Chrome 137 or later with Luau on, or does not fit the 13 MB gzipped budget. The spike tested only small hosts.
2. The init order or the shared allocator fails in the real `main` plus `spawn_app` path (the spike tested a `requestAnimationFrame` shape). Measure: in Chrome 137 or later, with the real engine module and `luau` on, `init()` resolves, 300 frames run with no trap, and a build that attempts a second `_initialize` still resolves `init()` (the once-guard works). A failure that survives one fix attempt fires the tripwire.
3. The 10,000-entity `update` misses 4 ms at the median in the real engine on the live loop, after the `realloc` and `alloc_zeroed` forwarding and a quiet-machine re-run. A p99 above 4 ms alone is a finding that SP9 reports and fixes (or proposes a tighter script budget for), not a fallback.
4. The SDK layer is not reliable in CI. Measure: the linked check of rule 3 (fixture linked, `_initialize` exported, the `wasi_snapshot_preview1` imports a subset of the eight) fails for a reason that comes from the SDK or its layer (download, checksum, link error) and survives one fix attempt, or the clean Linux release build of the same fixture with `luau` on takes more than 10 minutes longer than the same build with `luau` off (the spike: about 32 s extra in release and about 60 s in debug).
5. Existing wasm benches regress by more than 5% with the wasi-libc allocator (rule 6) and the cause is the allocator, not the benches.

## Alternatives considered

- **Route B: a separate Luau wasm module bridged from JS.** It works (E6): 583 KB gzipped, 28 to 33 ns per host call. But it has two linear memories, so every entity, component and string crosses by copy. Reflection-derived bindings, userdata handles and the command bus would need a second binding layer on the web next to mlua on Windows. It needs the same SDK and `exnref`, so it saves no toolchain cost. Kept as plan B if route A breaks, before the native-only fallback.
- **Native-only scripts with a cfg-gated stub (owner decision 3).** Cheaper in toolchain, but web examples could not run any Luau, and the spike shows the cost is acceptable. Kept as the fallback and as the default SDK-free build.
- **`wasm32-unknown-emscripten`.** Replaces the whole web toolchain (`wasm-bindgen`, `winit`, `wgpu`) for scripting's sake. Not tried.
- **A pure-Rust Lua VM.** The ones the spike knew of target Lua 5.x, not Luau: no types, vectors or sandbox, and it changes the scripting contract. Not tried.
- **Build the legacy exception ABI too (Chrome 113 to 136).** A second set of SDK libraries and a runtime switch, for browsers outside the audience. Rejected for the MVP (rule 8).
- **`RUSTFLAGS` or a global `LUAU_CXXFLAGS` instead of `build.rs` and target-scoped variables.** `RUSTFLAGS` applies to every crate and breaks crates compiled before the libraries are found, and an unscoped C++ flag set would feed wasm flags to native Luau builds.
- **Make `luau` a default feature, or let the facade enable it.** Every `--workspace` build and every agent worktree would then need the SDK (rule 1).
- **Let `exitium_script` declare the global allocator.** It can be in a graph without the facade, and a final binary has only one. The facade is the one library in every game's graph exactly once (rule 6).
- **Let each game or bench binary declare it (as #64 does on native).** A game could forget it, and on wasm with `luau` a missing static means two untested heaps. Rejected for that configuration only (rule 6).

## Consequences

- **Easier.** Scripts run on the web with one VM and one binding layer. The workspace's own definition of done is unchanged for agents: the SDK-free stub keeps `cargo build --workspace --target wasm32-unknown-unknown` working.
- **Harder.** The Linux CI image needs a 192 MB SDK layer. `cargo xtask ci all` is no longer exactly what CI runs when the SDK is absent locally, so CLAUDE.md's definition of done gains one line. Script games on the web need Chrome or Edge 137. The web build links wasi-libc's allocator for all Rust code when `luau` is on, a new risk the existing wasm benches must show is within 5% (rule 6, tripwire 5).
- **High-risk areas touched downstream** (extra reviewer scrutiny, ADR-0005): the new `cc` and `mlua` dependencies, the `unsafe` forwarding allocator, CI and runner config, the `exitium` facade, and the licence notice.
- **Spike open questions, closed.** Q1 legacy ABI: not built, floor 137 (rule 8). Q2 allocator owner: the facade, gated, with an `alloc-stats` swap for #64's counter (rule 6). Q3 allocator behaviour: still open. SP9 benchmarks it and tests whether the forwarding is needed at all (rule 6, tripwires 3 and 5). Q4 `wasm-opt` in the export step: this ADR fixes only the failure mode and the flag list (rule 7); whether `exitium export` runs it, and the pinned binaryen, are decided in the export spec (#155).
