# Spec: ECS scheduler, system access, commands, resources and events

- Issue: #22 (amended by #138 / SP2: the parallel executor on `exitium_tasks`, `par_iter_mut`, non-send resources and script systems, executor and job spans, the 1M-entity and min-spec benchmarks, and the profiler-level decisions for Tracy, frame stats and the counting allocator)
- Crates: exitium_ecs (depends on exitium_core, exitium_reflect, exitium_profiler, **exitium_tasks** and, via the derive re-export, exitium_ecs_derive; see "Intake wiring"). Also governs `exitium_tasks` (spans, the `profiling` edge) and `exitium_profiler` (Tracy, frame timings, counting allocator): see "Profiler and tasks amendments".
- Status: draft

## Goal

Define how systems declare the data they touch, how the scheduler proves two systems cannot conflict, how order is expressed, how structural changes are deferred (`Commands`), how global data and messages work (resources, double-buffered events), and how an executor runs all of it. The storage spec (`ecs-storage-queries.md`, #21) already provides the primitives this spec builds on: `FilteredAccess`, `UnsafeWorldCell`, `TickWindow` and the cursor and sweep API. The job system spec (`tasks-job-system.md`, #19) provides `scope` and `parallel_for`, used by the parallel executor and by `par_iter_mut`. Reflection (`reflect-model.md`, #20) provides `TypeData` hooks.

**Full MVP scope (owner decision 2026-11-24, `mvp-roadmap.md` is the plan of record; it replaces the Jam cut of 2026-11-18).** Nothing here is cut. `exitium_ecs` depends on `exitium_tasks` from intake 1 (the edge is `exitium_ecs -> exitium_tasks`), so the **parallel executor (#48)**, **`par_iter_mut`**, the executor and job spans (#65), the 1M-entity parallel benchmark (#52) and the min-spec profile (#66) are all MVP. The consequence for the lanes is that the ECS lane never runs beside the tasks lane (roadmap R3): the tasks lane (#26 to #30) finishes first. Two executors share one `Plan`: the single-threaded executor is built first (item 12) and stays as the fallback for one thread and for `wasm32`; the parallel executor is built on the same seam (item 20b), after `par_iter_mut` (item 20a). `ExecutorKind` stays `#[non_exhaustive]`. Systems that must stay on one thread (Luau script systems, platform handles) are **exclusive or main-thread systems**: barrier nodes that run alone on the calling thread, with `NonSend` access to resources that are not `Sync` (see "Non-send resources and script systems").

Design in one paragraph: a **system** is a plain function whose parameters (`Query`, `Res`, `ResMut`, `NonSend`, `NonSendMut`, `Commands`, `EventReader`, `EventWriter`, `Local`) each report an access at build time. A **`Schedule`** collects systems, orders them by `before`/`after`/sets, derives conflict edges from the access sets, inserts **sync points** where deferred `Commands` must apply, and compiles all of that into an immutable `Plan` (a DAG in a stable topological order). An **executor** runs the plan: the single-threaded executor walks it in order on one thread, the parallel executor runs conflict-free nodes at the same time as jobs on `exitium_tasks`. A **`Schedules`** resource maps a `ScheduleLabel` to a `Schedule`, and the app crate decides which labels exist and in what order they run each frame.

## Non-goals

Not in v1 (each has a stated extension path, so none blocks sidescroller, isometric, pixel art, multiplayer or destruction):

- **Run conditions** (`run_if`), state machines and `OnEnter`/`OnExit`. State gating is done by running different schedules by label (the app decides). A condition would be a read-only system whose access merges into its target's access.
- **Nested sets, set-level conditions, `ParamSet`, system piping and system input/output values.** Two queries with provably disjoint filters can coexist in one system, which covers most `ParamSet` uses.
- **Parallel script systems.** A script system is exclusive (one Luau state, not `Sync`). One state per worker is an extension, not part of v1.
- **Observers, component hooks, removal events.** Same non-goal as the storage spec.
- **Determinism.** Not required (INTERVIEW #10). See "Determinism".
- **Changing a schedule through MCP.** Systems are Rust code in the MVP (gameplay is Rust only), so no editor feature edits them, and agent parity is not violated.
- **The Phase 4 command bus, the app loop, `Time`, `Transform2d` and the schedule names.** Owned elsewhere ("Boundaries").

Unsafe additions to the storage spec's inventory (it has three designated modules):

- `world/cell.rs` (designated #2) gains resource accessors (typed `&'w R` and `Mut<'w, R>` from a cell) and the **shared-state accessors that a job needs because it holds only a cell, not a `&World`**: `UnsafeWorldCell::increment_change_cursor(&self) -> ChangeCursor` (the atomic counter, the same operation as `World::increment_change_cursor`), `resolve_cursor(&self, ChangeCursor) -> Result<Tick, CursorExpired>` (the storage spec's error name), and `entities(&self) -> &'w Entities` (what `Commands` needs for `reserve_entity`, an atomic). All three are safe to call from any number of threads at once (atomics or reads of data that only `&mut World` can change), return no reference into a column, and are available on a read-only cell too. No new `unsafe` kind: the same contract, now stated **per `get_param` call** (see "Unsafe additions"), not per cell lifetime.
  - **The non-send accessors (item 23).** `NonSend::get_param` reads the value from a cell, so designated #2 also gains `UnsafeWorldCell::non_send_resource<R: 'static>(&self, ResourceId) -> &'w R` and, on a writable cell only, `non_send_resource_mut<R: 'static>(&self, ResourceId) -> Mut<'w, R>`. Each forwards to the slot in `world/non_send.rs` (designated #6), whose **owner-thread check runs inside, before any pointer is formed**, and panics naming the resource and both thread ids. They are not callable from a job (a job holds a `Send` cell, but the returned reference is `!Send` and the check fails off the owner thread), and the plan never runs a main-thread system as a job anyway. The per-call contract is the same as for the typed `Res` and `ResMut` accessors: the system's access set names the resource id.
- **Designated #4: `system/param.rs` and `system/function.rs`** (one invariant set, two files). Invariants are listed under "Unsafe additions".
- **Designated #5: `schedule/parallel.rs`** (#48), with Miri tests of its own. Its only `unsafe` is the `run_unchecked` call.
- **Designated #6: `non_send.rs`**, the owner-thread slot that lets a `!Send` value live in a `World` that is `Send + Sync`, with Miri tests of its own.

The single-threaded executor adds no `unsafe`: it calls the **safe** `System::run(&mut self, &mut World, ..)`, which builds the writable cell internally from the exclusive `&mut World`. The parallel executor calls `run_unchecked` only for systems that may share a segment (never for an exclusive or main-thread system), and runs barrier nodes through the same safe `run`.

### Systems, parameters and access sets

`System` is **sealed** (a private `sealed::Sealed` supertrait, implemented only by `FunctionSystem` and the exclusive-function system in this crate). Reason: the parallel executor's `// SAFETY:` argument rests on the access set a system reports being exactly what it touches; a downstream `impl System` could return a false `SystemAccess` and be scheduled beside a conflicting system. Users write systems as functions through `IntoSystem`, never by implementing the trait. (`SystemParam` below is sealed for the same reason.)

```rust
pub trait System: sealed::Sealed + Send + 'static {
    fn name(&self) -> &'static str;                      // type_name of the fn item, or the `.named(..)` override
    fn identity(&self) -> TypeId;                        // TypeId of the fn item type, used by after_system/before_system
    fn initialize(&mut self, world: &mut World) -> Result<SystemAccess, AccessError>;   // registers ids, builds QueryStates, fills access
    fn is_exclusive(&self) -> bool;
    fn runs_on_main_thread(&self) -> bool;               // exclusive, or has a NonSend/NonSendMut param: a barrier node, calling thread only
    fn has_deferred(&self) -> bool;                      // owns a Commands buffer
    fn run(&mut self, world: &mut World, window: TickWindow);          // safe: exclusive world, builds the writable cell inside
    /// # Safety: see "Unsafe additions". Never called by the single-threaded executor.
    /// Panics on a main-thread system (exclusive or non-send, which need `&mut World` and the calling thread);
    /// the parallel executor never calls it for one.
    unsafe fn run_unchecked(&mut self, world: UnsafeWorldCell<'_>, window: TickWindow);
    fn apply_deferred(&mut self, world: &mut World) -> ApplyReport;
}

pub trait IntoSystem<Marker> { type System: System; fn into_system(self) -> Self::System; }
// Implemented by a macro for FnMut(P0..Pn) with n <= 8 and each Pi: SystemParam, and for fn(&mut World) (exclusive).
```

**Systems run as jobs.** Under the parallel executor a system body runs inside a `exitium_tasks` job, so the tasks spec's **job rule** applies to every system: a system must not block on anything that needs another system or job to run (a channel `recv`, a barrier, a condvar waiting on a sibling, a lock that another system holds across a `scope`, a thread-local `RefCell` borrow held across `par_iter_mut`). Order is expressed with `before`/`after`, never by waiting. The same rule holds for the single-threaded executor, where a violation is a deterministic hang in tests instead of a rare one.

`SystemParam` is a sealed `unsafe trait` (users cannot add params in v1, so the access claim cannot be forged):

```rust
pub unsafe trait SystemParam: Sized {
    type State: Send + 'static;                          // per-system storage: QueryState, EventCursor, Local<T> value, CommandQueue
    type Item<'w, 's>: SystemParam<State = Self::State>; // what the function receives
    fn init_state(world: &mut World, access: &mut SystemAccess) -> Result<Self::State, AccessError>;   // adds this param's access
    /// # Safety: the access added in `init_state` is exactly what the returned item can touch,
    /// and no conflicting access exists **while any item or pointer derived from this call is live**
    /// (one system run; the caller proves it, see Unsafe additions). The cell may be shared with
    /// other systems that are ordered against this one: only the call's own live window counts.
    unsafe fn get_param<'w, 's>(state: &'s mut Self::State, cell: UnsafeWorldCell<'w>, window: TickWindow) -> Self::Item<'w, 's>;
    fn apply_deferred(_state: &mut Self::State, _world: &mut World) -> ApplyReport { ApplyReport::default() }
}
```

| Param | Access | Notes |
|---|---|---|
| `Query<'w, 's, D, F = ()>` | the query's `FilteredAccess` (reads, writes, tick_reads, with, without) | Read side, `&self`, bounded `D: ReadOnlyQueryData`: `iter`, `get`, `single`, `is_empty`, `count`. Write side, **`&mut self`**, items borrow the param: `iter_mut`, `get_mut`, `single_mut`, `iter_chunks_mut`, `par_iter_mut` (#48, "Parallel query iteration"). Every call goes through the storage `_with` forms with the **run's** `TickWindow` (hand-off 1 below). The `&mut self` rule is what keeps two live `Mut<T>` for one entity impossible in safe code (invariant 3 under "Unsafe additions") |
| `Res<'w, R>` / `Option<Res<R>>` | resource read | `Deref`; `is_changed()`, `is_added()` against the run's window. Missing resource: panics naming system and resource; `Option<Res<R>>` yields `None` |
| `ResMut<'w, R>` / `Option<ResMut<R>>` | resource write | wraps the storage `Mut<R>`: stamps `this_run` on `DerefMut` only, `bypass_change_detection()` available |
| `NonSend<'w, R>` / `NonSendMut<'w, R>` (`R: 'static`, no `Send` or `Sync` bound) | resource read / write on the non-send resource's id, **and `main_thread = true`** | `Deref` / `DerefMut` like `Res`/`ResMut` (same tick rules). The item is `!Send` (compile-fail doctest). A system with one of these is a barrier node that runs on the calling thread ("Non-send resources and script systems"). Missing resource: panics naming system and resource; `Option<NonSend<R>>` yields `None` |
| `Commands<'w, 's>` | none (reserves entity ids atomically through `&Entities`) | owns the system's `CommandQueue` as state; `has_deferred` is true |
| `EventReader<'w, 's, E>` | read of the resource `Events<E>` | the per-system `EventCursor` is its state |
| `EventWriter<'w, E>` | write of the resource `Events<E>` | two systems writing the same `E` serialize; that is the price of a plain `Vec` push and is fine at game event rates |
| `Local<'s, T: Default + Send + 'static>` | none | per-system value, lives as long as the system |

**Single-entity `Query::get`/`get_mut` use the run's window.** `Query` is built from `QueryState::get_with`, `get_mut_with` and `iter_with` with `TickWindow { last_run, this_run }`, so a system's single-entity write stamps `this_run`, never `world.change_tick()`. This closes hand-off 1 of the storage spec ("Downstream issue adjustments", #22); the end-to-end test is in the Test plan.

**Exclusive systems** are `fn(&mut World)`, or a closure `FnMut(&mut World) + Send + 'static` through `exclusive(name, f)` (below). They are a safe type (no params, no state beyond the function), their `SystemAccess` is `exclusive = true`, and they conflict with everything. They are not a "run" for tick purposes: their world-level writes stamp `world.change_tick()` like any other world-level write.

**Main-thread systems** are exclusive systems and systems with a `NonSend` or `NonSendMut` param. `SystemAccess.main_thread` is true for both, and a main-thread system is a **barrier** exactly like a sync point: it conflicts with everything, runs alone, on the calling thread, through the safe `System::run`. The plan treats `exclusive || main_thread` as one barrier flag, so the graph compiler and the executors need one rule.

```rust
pub fn exclusive(name: impl Into<Cow<'static, str>>, f: impl FnMut(&mut World) + Send + 'static) -> SystemConfig;
```

`exclusive` builds a dynamic exclusive system for hosts that create systems at run time (script systems, tests). The name is **interned** into a `&'static str` once (a process-wide table, bounded by the number of distinct names, which is bounded by the number of scripts), so `System::name` and `current_system()` keep their signatures. A dynamic system's `identity` is its closure type, so `after_system` cannot name it: order it with sets (`in_set`, `before_set`, `after_set`). `SystemConfig::named` takes `impl Into<Cow<'static, str>>` (a `&'static str` still works).

**Access data:**

```rust
pub struct SystemAccess {
    queries: Vec<FilteredAccess>,          // one per Query param: component reads/writes/tick_reads and with/without filters (storage spec)
    resources: Access,                     // reads/writes over ResourceId bitsets
    exclusive: bool,
    main_thread: bool,                     // exclusive, or any NonSend/NonSendMut param
    has_deferred: bool,
    combined: CombinedAccess,              // unions of the above for the O(words) fast-path test
}
```

**The conflict rule (the whole definition).** Systems `a` and `b` **conflict** when any holds:

1. `a.exclusive || b.exclusive || a.main_thread || b.main_thread`.
2. A resource is written by one and read or written by the other.
3. A query pair `(qa, qb)` with `qa` from `a` and `qb` from `b` has a component that one writes and the other reads or writes **and** the pair is not filter-disjoint. `tick_reads` count as reads (a `Changed<A>` reader never runs beside an `A` writer, as the storage spec requires).

Two queries are **filter-disjoint** iff some component is in `qa.with` and `qb.without`, or in `qb.with` and `qa.without`: no archetype can match both, so they can never touch the same row. `Option<&T>` adds no `with`. The same pairwise rule, applied to the params of **one** system, rejects the system at `initialize` with `AccessError::ParamConflict { system, param_a, param_b, name }` (for example `fn(Query<&mut Pos>, Query<&Pos>)`, or `Res<R>` with `ResMut<R>`), unless the two queries are filter-disjoint. A conflict inside a single `Query<D>` is the storage spec's `QueryAccessError`. Fast path: `combined` unions are tested first with a bitset AND (about 8 words per pair); only a hit pays the pairwise filtered test.

`FilteredAccess` must expose `with`/`without` (or `is_disjoint(&other)`); see "Downstream issue adjustments".

### Resources

```rust
pub trait Resource: Send + Sync + 'static {}              // hand impl, or #[derive(Resource)] (Implementation issues)
pub struct ResourceId(u32);                               // dense, per-process, never persisted (same rule as ComponentId)
pub struct Resources {
    by_type: HashMap<TypeId, ResourceId>,                 // in-crate multiplicative hasher, as the storage spec
    infos: Vec<ResourceInfo>,                             // { name: &'static str, type_id, tracked: bool }
    slots: Vec<Option<Column>>,                           // a Column of capacity 1: value, added/changed TickCell, drop_fn
}
```

- **Storage reuses `Column`** (designated #1, already `Send + Sync`, aligned, with tick arrays and the destructor shim) with `len` 0 or 1. The resource value is a typed `*mut R` from the column's base pointer, so no new `unsafe` kind exists and no `Box<dyn Any>` with its own `Sync` story is needed. Resources always track changes.
- **Ids are registered under `&mut World`**, like components: `World::init_resource_id::<R>()` is implicit in `insert_resource` and in `Res<R>::init_state`. A system can therefore name a resource that is inserted later (a Startup system, `Commands::insert_resource`). A separate id space from `ComponentId`: a type that is both a `Component` and a `Resource` causes no false conflict.
- **Ticks:** `insert_resource` of a new resource stamps `added = changed = world.change_tick()`. Overwriting an existing resource stamps `changed` only (same rule as an overwrite-insert of a component). `ResMut` stamps `this_run` on `DerefMut`. `remove_resource` then `insert_resource` is a fresh `added`. `Res::is_changed()` is `is_newer_than(changed, window.last_run, window.this_run)`; the first run (`last_run == None`) sees every resource as added and changed, which is intended (initial UI binding).
- **Structure changes need `&mut World`** (`insert_resource`, `remove_resource`, id registration), so resource slots never move during a run. Systems insert through `Commands`.
- `AppTypeRegistry` is a `Resource` through `impl Resource for AppTypeRegistry` (#50; reflect-model, "Registry ownership").

```rust
impl World {
    pub fn insert_resource<R: Resource>(&mut self, value: R);
    pub fn init_resource<R: Resource + Default>(&mut self);                 // no-op if present
    pub fn contains_resource<R: Resource>(&self) -> bool;
    pub fn get_resource<R: Resource>(&self) -> Option<&R>;
    pub fn resource<R: Resource>(&self) -> &R;                              // panics, message names R
    pub fn get_resource_mut<R: Resource>(&mut self) -> Option<Mut<'_, R>>;  // stamps world.change_tick() on DerefMut only
    pub fn resource_mut<R: Resource>(&mut self) -> Mut<'_, R>;
    pub fn remove_resource<R: Resource>(&mut self) -> Option<R>;
}
```

### Non-send resources and script systems

A **non-send resource** is a value that is not `Sync`, and not necessarily `Send`, and must stay on one thread: the Luau state (one VM, not `Sync`), and on `wasm32` possibly GPU handles (Open question 5, resolved below). The `World` stays `Send + Sync`, so the value cannot sit in a plain `Resource` slot.

```rust
impl World {
    pub fn insert_non_send_resource<R: 'static>(&mut self, value: R);                  // records the calling thread as the owner
    pub fn contains_non_send_resource<R: 'static>(&self) -> bool;
    pub fn non_send_resource<R: 'static>(&self) -> &R;                                  // panics off the owner thread: message names R and both threads
    pub fn non_send_resource_mut<R: 'static>(&mut self) -> Mut<'_, R>;
    pub fn remove_non_send_resource<R: 'static>(&mut self) -> Option<R>;               // owner thread only
    /// Lends the value and `&mut World` together: the value is moved out of its slot for the call and put back after it, also on unwind.
    pub fn non_send_resource_scope<R: 'static, T>(&mut self, f: impl FnOnce(&mut World, &mut R) -> T) -> T;
}
```

- **Storage.** A `NonSendSlot { owner: ThreadId, value: UnsafeCell<Option<Box<dyn Any>>>, added: TickCell, changed: TickCell }` per id in `world/non_send.rs` (**designated #6**). The two `TickCell`s (an `AtomicU32` each, so `Send + Sync` without `unsafe`) live **in the slot, beside the value**, because a non-send value is not in a `Column`; reading or stamping them does not touch the value, so they need no thread check, and `NonSend::is_changed` is the same `is_newer_than` test as `Res`. The slot shares the `ResourceId` space and the access bitsets of `Resource` (so conflicts and `Res`-style change detection work unchanged), with `ResourceInfo.non_send = true`. A type inserted as both a `Resource` and a non-send resource is a panic at insert (the id is one kind).
- **Why it is sound.** `unsafe impl Send + Sync for NonSendSlot` rests on one rule: **the value is created, read, written, moved and dropped only on the owner thread**, checked on every access with `thread::current().id() == owner` (about 5 ns, a thread-local read; a constant on `wasm32`). A `World` that moves to another thread keeps the slot but can no longer touch it: access panics naming the resource and both thread ids. **Drop off the owner thread leaks the value** (`mem::forget`, never a destructor on the wrong thread; a debug build also asserts), which is safe and bounded to shutdown. The item type of `NonSend`/`NonSendMut` is `!Send`, so a system cannot hand the borrow to a job.
- **Who is the owner.** The thread that inserted the value. The app loop builds and runs the `World` on one thread, so the thread that calls `Schedule::run` is the owner. A main-thread system runs on exactly that thread (barrier nodes run on the calling thread, "Parallel executor").
- **Reflection.** Non-send values are not reflected (`ReflectResource` needs `Send + Sync`). `ResourceInfo` lists them with `non_send = true`, so an agent sees that they exist and cannot read or write them.
- **Ticks.** The same rules as `Resource`: a new value is `added = changed = world.change_tick()`, `NonSendMut` stamps `this_run` on `DerefMut` only.

**How script systems run.** A Luau script system is an **exclusive** system registered through `exclusive(name, f)` by `exitium_script` (SP9 owns the registration, the sets and the hot reload). The closure holds only ids and calls `world.non_send_resource_scope::<ScriptVm, _>(|world, vm| vm.run(world, ..))`, so the VM and `&mut World` coexist for the call. Because it is exclusive, it is a barrier node: it runs **alone, on the calling thread, never beside another system, never inside a segment**, so the Lua state is never touched from two threads and never needs `Sync`. Scripts are ordered against Rust systems by sets. The cost is one barrier per script system run; a game with many script systems puts them in one set and one schedule slot, which the sim bench in the script spec measures. A system written in Rust that needs `NonSend` access (a platform window handle, say) is the same kind of node.

### Events (double-buffered)

```rust
pub trait Event: Send + Sync + 'static {}
pub struct Events<E: Event> { old: Vec<E>, new: Vec<E>, old_start: u64, new_start: u64, count: u64 }  // a Resource
pub struct EventId(u64);                                  // the event's index in send order, monotonic, never reused
pub struct EventCursor { next: u64, missed: u64 }         // per reader; state of EventReader, or held by hand
#[derive(Copy, Clone, Eq, PartialEq)] pub enum EventClock { Frame, Fixed }
```

- `send` pushes onto `new` and returns the `EventId`. `count` is the number of events ever sent (`u64`, so it cannot wrap on wasm32).
- **`Events::update()` swaps the buffers:** the old buffer is dropped (its `Vec` is cleared, capacity kept), `new` becomes `old`, `new_start = count`. **Lifetime:** an event sent between update `k` and update `k + 1` is readable until update `k + 2` drops it, that is, for two update intervals. A reader that runs at least once per interval sees every event **exactly once**.
- **Reader cursors:** `EventCursor::read(&mut self, &Events<E>) -> impl Iterator<Item = &E>` yields events with id `>= cursor.next` (old buffer first, then new), advancing `next` per item yielded, so an iterator dropped early leaves the rest for the next call. If `cursor.next < old_start` the events in between were dropped: the cursor jumps to `old_start` and adds the gap to `missed`. `EventReader::{read, len, is_empty, clear, missed}` wrap this; `clear` marks everything as read. A new `EventReader` starts at `next = 0`, so it reads whatever is still buffered.
- **Who calls `update`, and when.** `World::register_event::<E>(clock)` inserts `Events<E>` and records an erased `update` function in an `EventRegistry` resource, tagged with its clock. `World::update_events(clock)` calls every update registered for that clock. **The driver (`exitium_app`) calls `update_events(Frame)` once per rendered frame and `update_events(Fixed)` once after each fixed-step run.** Pitfall this design addresses: with a 60 Hz fixed schedule on a 144 Hz display, a `FixedUpdate` reader runs on some frames only, so an event sent in `Update` could expire before it runs; events that are produced and consumed in the fixed schedule use `Fixed`, and `EventReader::missed()` makes a leftover mismatch visible instead of silent. `Frame` is the default of `App::add_event` (app spec).
- A system that needs an event type that is not registered fails at `initialize` with `AccessError::UnregisteredEvent { name }` (message: call `register_event`), never at the first run.
- `World::send_event(e)` is a convenience over `resource_mut::<Events<E>>().send(e)` for exclusive code, tests, MCP (`ecs_send_event`) and the command bus. Events carry no change ticks.

### Commands (deferred structural changes)

```rust
pub trait Command: Send + 'static {
    fn apply(self: Box<Self>, world: &mut World);
    fn reserved_entities(&self, _out: &mut Vec<Entity>) {}         // spawn commands report the id they reserved (abandonment, below)
}
pub struct CommandQueue { cmds: Vec<Box<dyn Command>> }          // per system, reused across runs
pub struct Commands<'w, 's> { queue: &'s mut CommandQueue, entities: &'w Entities }
impl Commands<'_, '_> {
    pub fn spawn<B: Bundle>(&mut self, bundle: B) -> EntityCommands<'_>;   // reserves the id now: Entities::reserve_entity(&self)
    pub fn spawn_batch<B: Bundle>(&mut self, iter: impl IntoIterator<Item = B>);   // one reserve_entities(n) for n = size_hint
    pub fn entity(&mut self, e: Entity) -> EntityCommands<'_>;
    pub fn despawn(&mut self, e: Entity);
    pub fn insert_resource<R: Resource>(&mut self, value: R);
    pub fn remove_resource<R: Resource>(&mut self);
    pub fn add(&mut self, f: impl FnOnce(&mut World) + Send + 'static);    // custom command
}
impl EntityCommands<'_> { pub fn id(&self) -> Entity; pub fn insert<C: Component>(&mut self, c: C) -> &mut Self;
                          pub fn remove<C: Component>(&mut self) -> &mut Self; pub fn despawn(self); }
```

- **When buffers apply.** Never during a run. A buffer applies at a **sync point** of the schedule (rule below), always under `&mut World`, and always at the **end of the schedule run** (the last node of every plan is a sync point), so no buffer outlives its run.
- **How:** a sync node calls `world.flush_entities()` once, then `System::apply_deferred` on every system **in topological order**, each draining its queue in **recorded order**. So within one system, commands apply in the order they were issued; across systems, in plan order. Entity ids returned by `spawn` are valid for later commands in any buffer applied after the flush.
- **Dead or missing entities.** A command on an entity that no longer exists (despawned earlier in this or another buffer) is **skipped and counted**, not a panic: a crash on wasm aborts the page and an agent-written game needs a recoverable failure. `ApplyReport { applied, skipped_dead_entity }` is summed into `RunReport` and is visible to MCP (`ecs_get_stats` extension in the introspection issue). A skipped `spawn` is impossible because a reserved id is always live after the flush.
- **Cost of reservation.** Each `spawn` reserves one id (an atomic, within the storage spec's 20 ns / 60 ns contended budget); `spawn_batch` reserves all ids with one operation. A per-system reservation cache would cut the atomic further but needs `Entities` to take unused reservations back, which the storage spec does not provide; it is a perf follow-up (Open question 7). `World::spawn_reserved(&mut self, Entity, B)` places a flushed reservation straight into the bundle's archetype instead of an extra move out of the empty archetype (adjustment to #41).
- **Panics and abandoned runs (no phantom entities).** A panicking command or system abandons the run. `CommandQueue` records the ids it reserved (`reserved: Vec<Entity>`) and `Command::reserved_entities(&self, out)` lets a not-yet-run spawn command report its id. On abandonment the schedule calls `CommandQueue::abandon(&mut self, &mut World)` on every system's queue: it drops the unexecuted commands, then `world.flush_entities()` and **despawns each id those unexecuted spawn commands had reserved** (a spawn that already ran is a normal entity and is left alone). Without this, the next sync node's flush would turn every unflushed reservation into a live, component-less entity visible to `Query<Entity>` and `WorldStats`. Abandonment is done by `Schedule::run`'s unwind path on native; on `wasm32` a panic aborts, so there is nothing to clean. Dropping a `Schedule` that still holds pending buffers (only possible if its run was abandoned without a world) leaks the reserved index slots, a bounded one-off. The panic then propagates (see "Panic context"). Test in the Test plan.
- **Writes stamp the current tick.** Command application is a world-level write (storage spec, stamping rules), so `Changed<T>` observers see a system's own deferred commands in its **next** run, exactly once.

**Boundary with the Phase 4 command bus (different layers).**

| | `Commands` (this spec) | Command bus (`exitium_command`) |
|---|---|---|
| Producers | systems, during a run | editor, MCP, and any host code |
| Form | closure-like, not serializable, no undo | typed, serializable, with undo and history |
| Applies | at sync points **inside** a schedule run | **between** top-level schedule runs, never while a schedule runs |
| Failure | skips dead entities, counts them | returns a typed error to the caller, rolls back |
| Order | recorded order, then plan order | submission order |

The bus applies by calling `World` methods directly under `&mut World`; it does not go through `Commands`, and `Commands` never records undo. A bus command that spawns or despawns entities uses the same reserve/flush rules. Both are world-level writes, so both stamp `world.change_tick()` and bindings observe editor edits and system edits identically.

### Ordering, sets and the schedule graph

```rust
#[derive(Copy, Clone, Eq, PartialEq, Hash, Debug)] pub struct ScheduleLabel(&'static str);   // const fn new; "crate::name" convention
#[derive(Copy, Clone, Eq, PartialEq, Hash, Debug)] pub struct SystemSet(&'static str);        // flat, no nesting in v1

pub fn system<M>(f: impl IntoSystem<M>) -> SystemConfig;                  // erased, so arrays and Vecs hold mixed systems
impl SystemConfig {
    pub fn named(self, name: impl Into<Cow<'static, str>>) -> Self;        // required to add the same fn twice (interned, see exclusive())
    pub fn in_set(self, s: SystemSet) -> Self;
    pub fn before_set(self, s: SystemSet) -> Self;   pub fn after_set(self, s: SystemSet) -> Self;
    pub fn before_system<M>(self, f: impl IntoSystem<M>) -> Self;   pub fn after_system<M>(self, f: impl IntoSystem<M>) -> Self;
}
pub fn chain(systems: impl IntoIterator<Item = SystemConfig>) -> Vec<SystemConfig>;   // each runs after the previous one

impl Schedule {
    pub fn new(label: ScheduleLabel) -> Schedule;
    pub fn add_systems(&mut self, systems: impl IntoIterator<Item = SystemConfig>) -> &mut Self;
    pub fn configure_set(&mut self, s: SystemSet) -> SetConfig<'_>;        // .before_set / .after_set between whole sets
    pub fn build(&mut self, world: &mut World) -> Result<(), ScheduleError>;   // initialize new systems, compile the Plan
    pub fn run(&mut self, world: &mut World) -> RunReport;                 // builds first if dirty; panics on a build error
    pub fn report(&self) -> Option<ScheduleReport>;                        // introspection, None before the first build
}
```

Labels and sets are `&'static str` newtypes, not types, on purpose: a basic-level reviewer reads them at a glance, they need no derive or macro, and MCP can list them by name. The `crate::name` convention avoids collisions. `after_system(f)` names a system by the `TypeId` of its fn item type; a closure or a fn added twice needs `.named(..)`.

**Stages.** There are **no stages inside a schedule**. Coarse phases are sets chained with `configure_set(A).before_set(B)`. Coarse frame structure (Startup, fixed update, update, render extraction) is a sequence of **schedules**, which `exitium_app` runs in order. This replaces the "named stages" wording of #47.

**Fixed versus variable tick.** A fixed-rate schedule and a per-frame schedule are the same `Schedule` type. The only difference is cadence, which belongs to the driver: it runs the fixed schedule 0 to N times per frame and the variable one once. What the ECS guarantees for both: every `run` is a run for tick purposes (below), so a fixed schedule that runs three times in a frame sees changes made between its runs, and a schedule that does not run for a while simply has older `last_run`s. The catch-up cap and the `Time` swap are the app's.

**Build.** `build` runs once, lazily at the first `run`, and again only when systems were added. It:

1. Calls `initialize` on each new system against `&mut World` (ids, `QueryState`s, access); errors are `ScheduleError::Access`.
2. Builds the **explicit edges** from `before_*`/`after_*`/`chain`/`configure_set`. An edge to a set expands to every member; a set with no members contributes nothing; `after_system(f)` with `f` not in this schedule is `ScheduleError::UnknownSystem`. Two systems with the same identity **and the same name** is `ScheduleError::DuplicateSystem` (the same fn added twice needs `.named`; dynamic `exclusive` systems share an identity, so each needs its own name).
3. **Cycle check and levels.** Run Kahn's algorithm over the explicit edges only. A cycle is `ScheduleError::Cycle { systems: Vec<&'static str> }` naming the systems on one cycle (found by DFS over the leftover nodes). The same pass computes `level(n) = max(level(p) + deferred(p) as u32)` over explicit predecessors `p` (roots are 0), where `deferred(s) = s.has_deferred()`.
4. **Sync points.** For every level `k >= 1` that contains a node, add `SyncPoint(k)`: it is a successor of every deferred system with level `k - 1` and a predecessor of every node with level `k`. Add a final `SyncPoint(end)` that is a successor of every other node. Meaning: **a system explicitly ordered after a system that has `Commands` sees those commands applied**; unordered systems do not get that guarantee. A sync point and a main-thread system (exclusive or non-send) are **barriers** (they conflict with everything).
5. **Final order (where sync points sit).** Run Kahn again over explicit edges plus sync-point edges with a min-heap on this key: a system node has key `(registration_index, 1)`; `SyncPoint(k)` has key `(smallest registration index among its successors, 0)`, so it is picked immediately before its first-registered successor once its predecessors are done; `SyncPoint(end)` has key `(MAX, 0)`. The result is the plan's node order: stable, equal to registration order wherever nothing constrains it, with every sync point placed as late as its first consumer allows (so unrelated systems registered before that consumer run before the sync point). This order is observable (single-threaded run order, which unrelated systems the barrier waits for) and is pinned by a test.
6. **Reachability** over the explicit DAG (explicit plus sync-point edges; one bitset row per node, filled in reverse order of step 5).
7. **Conflict edges.** For each pair `(a, b)` with `a` earlier in the step 5 order that conflicts (rule above) and has **no** path from `a` to `b`: add the edge `a -> b`, and, when neither node is a barrier, record an **ambiguity** `(a, b, conflicting names)` (a sync point or main-thread system conflicts with everything by design, so those pairs are ordered but never reported). Conflicting pairs are thus always serialized, oriented by plan position (so by registration order when unconstrained). A pair that is already ordered adds no edge. Every added edge points forward in the step 5 order, so the order stays a valid topological order and no second sort is needed.
8. Emits the immutable `Plan`.

```rust
struct Plan {
    nodes: Vec<Node>,              // the step 5 order; Node = System(SystemId) | SyncPoint(level)
    preds: Csr, succs: Csr,        // flattened adjacency (offsets + targets, u32)
    segments: Vec<Range<u32>>,     // maximal runs of non-barrier nodes between barriers (parallel executor)
    seg_dep_count: Vec<u32>,       // preds of a node that lie in its own segment: the initial value of the parallel executor's counters
                                   // (a pred outside the segment is a barrier or an earlier segment, already finished when the segment starts)
    ambiguities: Vec<Ambiguity>,
}
pub enum AmbiguityCheck { Report, Deny }       // Schedule::set_ambiguity_check; default Report
```

Ambiguities are data, not log lines (the ECS has no logging dependency): `ScheduleReport` lists them, the app may print them, and a test can use `Deny` (build returns `ScheduleError::Ambiguous`) to forbid them. Two systems that conflict and are unordered are legal and deterministic in effect (see "Determinism"), but usually a missing `before`/`after`.

**Adding a system after the first build** marks the schedule dirty. Existing systems keep their state and `last_run`; only the new ones initialize. Removal is not offered in v1 (rebuild the schedule).

`run_schedule` **removes** the schedule from `Schedules` for the duration of the run (so systems can use `ResMut<Schedules>` for other schedules and `run_schedule` of other labels can nest), runs it under `catch_unwind` on native, **always reinserts it**, then resumes any panic. ### Executors and the run loop

```rust
#[non_exhaustive] #[derive(Copy, Clone, Eq, PartialEq, Debug, Default)]
pub enum ExecutorKind { #[default] SingleThreaded, Parallel }   // Parallel resolves to SingleThreaded on one thread and on wasm32
impl Schedule {
    pub fn set_executor(&mut self, kind: ExecutorKind) -> &mut Self;               // default SingleThreaded
    pub fn set_task_pool(&mut self, pool: Option<Arc<TaskPool>>) -> &mut Self;     // parallel executor only: its segments' scopes run on this pool; None (default): the pool the tasks crate resolves for the thread
}
pub struct RunReport { pub systems_run: u32, pub sync_points: u32, pub applied: u64, pub skipped_dead_entity: u64, pub sweep_slices: u32,
                       pub executor: ExecutorKind /* the one that ran: shows a fallback */, pub threads: u32 }
```

**Per-system run (both executors, the whole tick contract):**

```
this = world.increment_change_cursor()                          // atomic, returns the pre-increment value
last = entry.last_run.and_then(|c| world.resolve_cursor(c).ok())   // an expired cursor becomes None: everything is seen once
system.run(world, TickWindow { last_run: last, this_run: Tick::from(this) })
entry.last_run = Some(this)                                     // only after the run returned
```

In the single-threaded executor `world` is the `&mut World`. In the parallel executor a job holds only the segment's `UnsafeWorldCell`, so the first two lines call the cell's accessors of the same names (designated #2, "Unsafe additions" below) and the third is `run_unchecked(cell, window)`.

- **`last_run` is a `ChangeCursor` (64-bit), not a `Tick`.** This is a deliberate change from hand-off 2 of the storage spec, which asked the scheduler to clamp per-system `Option<Tick>` values with each `TickSweep`. A 64-bit cursor is resolved by age on every run, exactly like the standalone `QueryState` and external consumers in the storage spec, so there is **nothing to clamp**: it cannot alias after a wrap, it needs no registration, and it stays correct for schedules that are stored outside `Schedules`, run nested, or idle for a long time. An idle system whose cursor is older than 2^30 sees everything once (a false positive only, the same outcome as the clamp). Cost: one `resolve_cursor` per run (two compares). Open question 1 asks the owner to confirm.
- Exclusive systems and sync nodes do not increment: they are world-level (stamp `world.change_tick()`). A non-send system **with params** is an ordinary run (it increments and gets a window); it only differs in running as a barrier.
- A system's own `Commands` apply at a sync node after its run, stamping the current tick, so its **next** run sees them (the required storage-spec test) and never sees its own direct writes.
- A system that panics does not update `last_run`.

**Sync node:** `world.flush_entities()`; `apply_deferred` on every system with a non-empty queue in plan order; then **sweep polling**: `if world.needs_tick_check() { world.check_change_ticks(SWEEP_SLICE_TICKS) }` with `SWEEP_SLICE_TICKS = 1 << 19` (524,288 stored ticks). At the storage spec's budget of 2.5 ms per 4M ticks that is about 0.33 ms; even at twice that cost it is about 0.65 ms, inside the storage spec's "slices of <= 1 ms per sync point" bound. This meets the host poll contract ("at least once per 2^27 increments"): every schedule run ends in a sync node, and one run adds only as many increments as it has systems. The returned `TickSweep` needs no per-system application (cursors).

**System entries and `Send + Sync`.** `System` is `Send` but not `Sync` (a `FnMut` closure and its param state need only be sendable). `Resource` is `Send + Sync` and `Schedules` is a `Resource`, so `Schedule` must be `Sync` too. Rule: every system entry is `Mutex<SystemEntry { system: Box<dyn System>, last_run: Option<ChangeCursor> }>` in **both** executors. `Mutex<T>` is `Sync` when `T: Send`, so `Schedule: Send + Sync` follows with no `unsafe impl`. The two executors reach the entry differently. **The single-threaded executor takes no lock:** `Schedule::run` takes `&mut self`, so it calls `Mutex::get_mut`, which needs no atomic and costs nothing at run time. **The parallel executor locks** each entry once per run through `&self`, uncontended (about 15 ns, inside its 1.5 us dispatch budget), because its jobs share the schedule. **A poisoned entry is recovered in both executors** (`PoisonError::into_inner`, also on the `get_mut` path): a panic in either executor abandons the run and may poison the entry of the system that panicked, and the next run must work (tested for both executors). `System: Send + Sync` is rejected as an alternative: it would force every system parameter state (`Local<T>`, a script handle) to be `Sync` for no benefit.

**`SingleThreadedExecutor` (the default executor, and the permanent fallback).** Walks `plan.nodes` in order. A system node runs the per-system sequence; a sync node does the sync-node work. It is the default for a new `Schedule`, and the parallel executor hands every run to it whenever the pool has one thread and on `wasm32`. It follows the **same plan and the same sync-point rules** as the parallel executor, so a schedule means the same thing on every target. It never calls `run_unchecked` and contains no `unsafe`.

**Panic context.** Before each system the executor pushes `(schedule label, system name)` onto a `thread_local` **stack** and pops it when the system returns (`exitium_ecs::current_system() -> Option<(&'static str, &'static str)>` reads the top), so a panic hook (the app installs one) can print the failing system even on `wasm32`, where panics abort and `catch_unwind` does nothing. A stack, not a single slot, because a system that waits in a nested scope (`par_iter_mut`, a segment's `scope` on the calling thread) can run another system's job on the same thread (tasks spec, help-first waiting): the push/pop pair restores the outer context when the inner one finishes. The single-threaded executor never nests (depth 1); the parallel executor does. On native the executor also wraps each system in `catch_unwind` and rethrows `resume_unwind(Box::new(SystemPanic { schedule, system, payload }))`, leaving the original payload reachable. The run is abandoned: every queue is abandoned as described under "Panics and abandoned runs", `last_run`s of unfinished systems are unchanged, and the world satisfies the storage spec's invariants because destructors run after bookkeeping.

### Parallel executor (MVP, #48)

`ExecutorKind::Parallel` runs the **same `Plan`** as the single-threaded executor, with the same sync-point rules, so a schedule means the same thing on every target. It lives in `schedule/parallel.rs` (designated #5) and is built on `exitium_tasks::scope` (tasks spec, "Public API sketch").

- **Which pool.** `Schedule::set_task_pool(Some(pool))` pins an explicit `Arc<TaskPool>` (tests and benches that must not touch the process default). With `None` the executor calls the tasks crate's free `scope`, which resolves the pool of the job running on this thread, then the process default installed once by the facade's `ThreadingPlugin` (`TaskPool::set_default`; neither this crate nor `exitium_app` installs a pool), then the inline pool. Work that systems start inside a job (`par_iter_mut`, `parallel_for`) resolves to the **same pool** through the worker's thread-local, so there are no extra threads. A main-thread system or an exclusive system that calls `parallel_for` runs outside the scope and uses the default pool (documented, not a bug).
- **Single-thread fallback.** At the start of every run the executor reads `threads` (`pool.threads()`, or `current_threads()` when no pool is pinned). If `threads == 1` (`ThreadBudget::single()`, the inline pool) or the target is `wasm32`, the run is handed to the single-threaded executor: same plan, same results, no `scope`, no atomics. `RunReport.executor` reports what ran and `RunReport.threads` how many threads it had, so a silent fallback is visible. No `cfg` appears in ECS code for this: the tasks crate owns `wasm32` (tasks spec, "Wasm32 and single-thread behaviour").
- **Partitioning.** `plan.segments` are the maximal runs of non-barrier nodes between barriers (sync points and main-thread systems). The executor walks the plan in order. A **barrier** node runs alone on the calling thread with `&mut World` through the safe `System::run` (a sync point does the sync-node work, a script or other main-thread system runs its body). A **segment** runs inside **one** `scope`:
  1. On the calling thread, before the scope: reset the segment's counters, `counters[i].store(plan.seg_dep_count[i], Relaxed)`. The `Vec<AtomicU32>` is allocated once per `Schedule` and reused, so a steady-state run allocates nothing.
  2. Build one `UnsafeWorldCell::from_mut(world)` for the segment.
  3. Spawn a job for every node with `seg_dep_count == 0`, in plan order (earlier-registered systems start first).
  4. A job runs the per-system sequence (`increment_change_cursor`, `resolve_cursor`, `run_unchecked`, `last_run`), then for each successor in the segment does `counters[s].fetch_sub(1, AcqRel)` and spawns the successor's job when the old value was 1 (`Scope::spawn` from inside a job is allowed, tasks spec "Nested jobs"). The `AcqRel` pair makes every predecessor's writes visible to the successor.
  5. The end of the `scope` is the segment's barrier. The cell is dropped, and only then does the next barrier take `&mut World` again.
  Because the plan holds a conflict edge for every conflicting pair, **any two nodes that can run at the same time have no conflict**, which is exactly the precondition of `run_unchecked`. The calling thread helps run jobs while it waits (tasks spec, help-first waiting), so it also runs systems, but never a main-thread system, which only ever starts as a barrier.
- **`&mut` hand-out.** Each system entry (`Box<dyn System>` plus its `last_run`) sits in an uncontended `Mutex` (the type is shared with the single-threaded executor, which reaches it by `get_mut` and takes no lock; see "Executors and the run loop"), so a job obtains its `&mut` without `unsafe` (about 15 ns per system per run). A poisoned lock is recovered (`PoisonError::into_inner`) because a panic abandons the run anyway. `UnsafeWorldCell` is already `Send + Sync` (storage spec, designated #2), so no new `Send` wrapper exists; the only `unsafe` in designated #5 is the `run_unchecked` call, with a `// SAFETY:` that cites the plan's conflict edges.
- **Nested parallelism.** A system that calls `par_iter_mut` or `parallel_for` runs inside the segment's scope. The tasks spec's help-first waiting and its `HELP_DEPTH_LIMIT` rule bound the stack, so a segment with 64 systems that each nest `par_iter_mut` neither deadlocks nor overflows the stack (test in the Test plan).
- **Failure.** Each job wraps the per-system sequence in `catch_unwind` (native). On a panic the job stores the first `SystemPanic { schedule, system, payload }` in a `Mutex<Option<_>>` and sets a shared `AtomicBool`. Jobs that have not started check the flag first and return without running their system; in-flight jobs finish (the tasks spec has no cancellation); successors of the panicked system are never spawned. After the `scope` returns, the executor abandons every queue ("Panics and abandoned runs") and `resume_unwind`s the stored `SystemPanic`. A system that was skipped keeps its `last_run`. On `wasm32` a panic aborts and none of this runs.
- **Observability.** `RunReport.executor` and `.threads` (above); `exitium_ecs::schedule::segment` spans per segment ("Profiling hooks"); the pool's own counters through `tasks_get_stats` (tasks spec).

### Parallel query iteration (`par_iter_mut`, #48)

`Query::par_iter_mut` is the data-parallel half of the same feature. The storage spec ("Threading model") owns the iteration and the aliasing argument; this section owns the system-param surface.

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub enum Batching { Auto, Fixed(usize) }   // Auto: clamp(total_rows / (4 x threads), 256, 16_384); Fixed(0) panics (programmer error)
impl<D: QueryData, F: QueryFilter> Query<'_, '_, D, F> {
    pub fn par_iter_mut(&mut self, batching: Batching, f: impl Fn(D::Item<'_>) + Sync);
}
// Standalone: QueryState::par_iter_mut(&mut self, &mut World, Batching, f)  (storage spec)
```

- **Takes `&mut self`**, like every mutable `Query` form, so the aliasing contract (invariant 3) is unchanged: a second `iter_mut` or `get_mut` cannot be live while `par_iter_mut` runs.
- **The closure is `Fn + Sync`** and receives the item (`Mut<T>`, `&T`, `Entity`, tuples). Items are built **inside** the task from `Copy` raw-pointer `Fetch` values for the task's own rows, so no `Send` bound is needed on the item and no task holds a `&mut Column` (storage spec). The closure cannot touch the `World` (it has no handle), so no structural change can happen inside it.
- **Windows and ticks.** It goes through the same `_with` entry as `iter_mut` with the run's `TickWindow`: `Mut<T>` stamps `this_run` on `DerefMut` only, with relaxed atomic stores. `Changed<T>` observers see a parallel write in their next run exactly once. A standalone call increments the cursor once on the calling thread, like `iter_mut` (storage spec).
- **Serial fast path.** With `threads == 1` or `total_rows <= batch`, it calls the body once per row **inline, in ascending order**, with no scope and no job (tasks spec, serial fast path). This is also the `wasm32` path.
- **Panics.** The body's panic propagates like a tasks panic (every started chunk finishes, the first payload is resumed), then as the system's panic. Row order, chunk order and floating-point reduction order are unspecified (see "Determinism").
- **Not in v1:** a read-only `par_iter` (a read-only system already runs beside other systems, and a parallel read reduction wants chunk partials, which belongs to `exitium_tasks::parallel_for` called directly), and `par_iter_chunks_mut`. Both are additive.

### Determinism

**None is required or promised** (INTERVIEW #10). Specifically: the relative order of two systems with no conflict and no ordering is unspecified; entity ids returned by `Commands::spawn` depend on reservation order, which differs between runs under the parallel executor; `par_iter_mut` row order is unspecified; floating-point reductions across chunks may differ. As an implementation property (not a guarantee, tests may rely on it, games must not): two *conflicting* systems always run in plan order, commands apply in plan order, and the single-threaded executor runs the plan exactly in order, so a single-threaded run is repeatable on one machine **provided no system calls `par_iter_mut` or another tasks function on a multi-thread pool**. `set_task_pool` does not pin the pool seen by nested calls made on the calling thread of the single-threaded executor (a `SingleThreaded` schedule resolves the free functions through the thread-local, then the process default pool), so a system that calls `par_iter_mut` there still runs on the default pool, and its row order and floating-point reduction order are unspecified. Repeatability therefore needs one of: a single-thread default pool (`ThreadBudget::single()`, which the test suite and the baselines of the Performance table use), or bodies that do not depend on cross-row order (disjoint writes, `Batching::Fixed(n)` for reproducible chunk boundaries, per-chunk partials combined in chunk order). The parallel and single-threaded executors produce the same results for systems that communicate only through the ECS, up to the unspecified items above.

### Unsafe additions

The workspace deny stays. Designated #4 (`system/param.rs`, `system/function.rs`) **invariants** (each module's `//!` lists them):

1. **The contract is per call, not per cell.** `get_param` and `run_unchecked` are called only when **no conflicting access exists while any item or pointer derived from that call is live**, i.e. for the duration of one system run. A cell may outlive many runs and be shared by systems that conflict with each other, provided they are ordered so their runs never overlap. The caller proves it from the plan's conflict edges (the parallel executor) or from owning `&mut World` (the safe `System::run`, which builds `UnsafeWorldCell::from_mut` itself). Each run derives **fresh** raw pointers from the cell (`Fetch` values, column base pointers, tick pointers) and **caches none across runs**: `QueryState` caches only archetype indices and metadata, never data or tick pointers, and `Local` state holds no pointer into the world. So a pointer derived in one run can never be used after another system's conflicting run, and the happens-before between two ordered systems (designated #5 invariant 2) is enough to make the second run's accesses sound.
2. The cell is **writable (built by `from_mut`) whenever the system's access contains any write**; a read-only cell is passed only to systems whose access is read-only. This is enforced, not only promised: `FunctionSystem::run_unchecked` takes the cell's `is_writable()` and `debug_assert!`s `cell.is_writable() || !access.has_writes()` before any `get_param`.
3. For every param, the `SystemAccess` that `init_state` recorded is exactly what the item returned by `get_param` can touch (the reason the trait is `unsafe` and sealed). `Query` calls only the storage `_with` entry points, whose access matches the query's `FilteredAccess`.
   **Query aliasing contract.** The storage `_with` forms are `&self` and take a `Copy` cell, so safety against two live `&mut` to one row must come from the param's own signatures: `Query::iter`, `get` and `single` take `&self` and are bounded `D: ReadOnlyQueryData` (no `Mut` or `&mut T` item can exist); `Query::iter_mut`, `get_mut`, `single_mut` and `iter_chunks_mut` take **`&mut self`** and return items that borrow the `Query`, so a second `get_mut` (or an `iter` of the same query) while one is live does not compile. `Query` is not `Clone`/`Copy` and never exposes its cell. Compile-fail doctests pin both rules (Test plan).
4. A param item borrows `state` (`&'s mut`) and the cell (`'w`) and cannot outlive the call: the function bound is higher-ranked over `'w` and `'s`, so a system cannot stash a `Query` or `Res` past the call (compile-fail doctest).
5. `Commands` only reads `Entities` (atomic reservation) and mutates its own queue; it never touches components or resources before the sync point.
6. `QueryState` refresh (`update_archetypes`) happens in `get_param` under the same cell, which is sound because archetypes are only created under `&mut World`; the `WorldId` assert from the storage spec applies on every entry.

**Designated #5 (`schedule/parallel.rs`) invariants** (the module's `//!` lists them):

1. One **writable** cell (`from_mut`) per segment. It is created after the preceding barrier returned and dropped before the next barrier takes `&mut World`, and `scope` returns only when every job has finished (tasks invariant I1), so no cell-derived pointer outlives the segment. The borrow of `&mut World` for the segment is held by the compiler, so `&mut World` cannot be used while the cell is live. The cell is **shared by every system of the segment, including systems that conflict** (they are ordered by an edge); it is therefore the per-call contract of designated #4 invariant 1 that applies, not a claim about the cell as a whole.
2. A node's job starts only after every predecessor in its segment finished: the counter reaches 0 through `fetch_sub(1, AcqRel)`, so the predecessors' writes happen before the successor's reads. Nodes in different segments are separated by a barrier and the `scope` end.
3. This is the argument that discharges designated #4 invariant 1 for each `run_unchecked` call: **while system S's run is live (from its `get_param` to the end of its body), no job that conflicts with S is live.** Every conflicting pair has an edge in the plan (graph step 7), a successor is spawned only after its counter reaches 0 (invariant 2), so a conflicting successor cannot start before S's job returned, and a conflicting unordered pair is serialized by a conflict edge, so it is never live together. The executor adds no other way to start a node: it spawns only roots and counter-zero successors. Each run derives fresh pointers and caches none (designated #4 invariant 1), so nothing from S's run can be used by the successor.
4. `run_unchecked` is called only for a system with `runs_on_main_thread() == false`. The plan puts every other system in a barrier, and a `debug_assert!` repeats the check at the call.
5. Each `Box<dyn System>` is reached only through its own `Mutex`, so exclusive access to a system's state is safe code. The segment cell is always writable, so invariant 2 of designated #4 holds for every system.
6. On a panic the flag stops new starts, but no `unsafe` state is left half-built: the queues are abandoned under `&mut World` after the `scope` returned.

**Designated #6 (`world/non_send.rs`) invariants:** the value in a `NonSendSlot` is constructed, accessed (shared or exclusive), moved out (`non_send_resource_scope`, `remove_non_send_resource`) and dropped **only on the owner thread**, checked on every entry before any pointer is formed; drop on another thread leaks the value and never runs its destructor; the borrow handed out has the same shared or exclusive rules as a `Resource` borrow of the same id (the scheduler's access sets) and is additionally `!Send`; `non_send_resource_scope` puts the value back on unwind (a drop guard), and re-entrant access to a value that is currently lent out panics naming it.

Any later PR touching these files is high-risk: Miri tests, and the reviewer checks every `// SAFETY:` argument (ADR-0005). `crates/exitium_ecs/CLAUDE.md` must change from "exactly three" to the real count: done by the first issue that adds designated #4 (item 6), and again by the issues that add #6 (item 23) and #5 (item 20b).

## MCP / editor surface

Agent parity (rule 1) and reflection as source of truth (rule 2): components, resources and events are addressed by **stable type name** (reflection, #20); values travel as reflected JSON; no hand-written schema.

**This spec files no issue in `exitium_mcp` or `exitium_editor`.** #110 builds the MCP tools generically from reflection and the command registry, and the editor panels from reflection. What this spec owes #110 is a list of what must be exposed and the Rust API to expose it through; both are below and are delivered by `exitium_ecs` issues.

**Reflected types and read API (delivered in the MVP, in `exitium_ecs`):**

- **Resources.** `ReflectResource`, type data registered by `#[reflect(Resource)]` (already in the reflect spec's type-data table): `contains(&World)`, `get(&World) -> Option<&dyn Reflect>`, `get_mut(&mut World) -> Option<ReflectedMut<'_>>` (stamps in `as_reflect_mut` only, the same guard as `ReflectComponent`), `insert(&mut World, &dyn Reflect)`, `remove(&mut World)`, and the by-name **changed-since query** `is_changed_since(&self, world: &World, since: ChangeCursor) -> Option<bool>`. Every game resource that should be visible to an agent or the inspector is `#[derive(Reflect)]` plus `#[reflect(Resource)]`.
  - **Why it exists.** UI data binding (the UI spec binds a widget to a resource field by type name and path, with no Rust type in hand) needs the change tick of a resource it can only name, to skip re-reading a value that did not change. `Res<R>::is_changed` needs the type, and `get` returns the value without its ticks, so the by-name accessor is the missing piece.
  - **Semantics.** `None` when the resource is absent. Otherwise `Some(true)` exactly when the resource's `changed` stamp is newer than the tick that `since` resolves to, with the same `is_newer_than(changed, last_run, this_run)` test as `Res::is_changed`, where `last_run = world.resolve_cursor(since)` and `this_run = Tick::from(world.change_cursor())` (the current counter; nothing is incremented, so it takes `&World` and is safe from any system with `&World` or a read-only cell). **An expired cursor counts as changed:** if `resolve_cursor` returns `CursorExpired` (the cursor is older than 2^30, or is at or above the counter, for example a plain `change_cursor()` read) the answer is `Some(true)`, a false positive only, the same outcome as a system whose cursor expired sees every change once. It never panics on a bad cursor.
  - **How a binding uses it.** Poll with the cursor kept from last time, then mint the next one with `world.increment_change_cursor()` and keep it as the next `since`. A write that happened before the poll stamps a value at most the pre-increment counter, so it is seen by this poll and is **not** newer than the minted cursor, so the next poll does not see it again (exactly once). This needs **no writer between the poll and the mint**, which holds when the binding runs as an exclusive or main-thread system, or between schedule runs (the UI binding step does); a write racing in between would be lost, not doubled. The by-name query adds no cell accessor and no `unsafe`: it reads the resource's `changed` `TickCell` (an `AtomicU32`) through `&World`.
  - It is a hand-written method on the `ReflectResource` struct (a function pointer built by `ReflectResource::from_type::<R>()` like the others), not a reflect-derive feature, and it appears in the MCP read surface only through the existing resource tools (an agent has no use for a cursor here).
- **Events.** `ReflectEvent` carries `send(&mut World, &dyn Reflect) -> Result<EventId, ApplyError>`. The reflect spec has no `#[reflect(Event)]` (it registers only `Default`, `TextForm`, `Component`, `Resource`), so registration is a **hand-callable** `World::register_reflected_event::<E>()` (which calls `registry.register::<E>()`, registers `ReflectEvent` and `register_event::<E>(clock)`'s `Events<E>`); `App::add_event` (app spec) calls it for reflected events. If the reflect spec later adds an attribute, it only calls this function. No reflect-derive change is required now.
- **Introspection structs.** `ScheduleReport`, `SystemReport`, `Ambiguity`, `ResourceInfo`, `EventInfo` and `RunReport` derive `Reflect` and are returned by plain read functions: `World::schedule_labels()`, `World::schedule_report(label)`, `World::resource_infos()`, `World::event_infos()` and the last `RunReport` per label (`Schedules::last_report(label)`). `ScheduleReport { label, executor, order, systems[{ id, name, sets, reads, writes, resource_reads, resource_writes, exclusive, main_thread, deferred, ordered_after }], sync_points[], ambiguities[{ a, b, conflicting }] }`. `executor` is the schedule's configured `ExecutorKind` (what `RunReport.executor` says actually ran may differ after the single-thread fallback). `main_thread` is true for a system that reads or writes a non-send resource (barrier, runs on the calling thread). Names are `ComponentInfo`/`ResourceInfo` type names; #110 maps them to stable names through the registry. `ResourceInfo` carries `non_send: bool`; non-send resources are listed (so an agent sees that a `ScriptVm` exists) but are **not** reflected: `ReflectResource` is never registered for them, so `ecs_get_resource` and the resource commands reject them with a typed error, because a value pinned to one thread cannot be serialized from the MCP thread.

**Commands the bus must expose (mutation always goes through the command bus, rule 3, applied between schedule runs, each with undo):**

Suggested tool names for #110, `<domain>_<verb>`: `ecs_list_schedules`, `ecs_get_schedule`, `ecs_list_resources`, `ecs_get_resource`, `ecs_list_events`, `ecs_insert_resource`, `ecs_remove_resource`, `ecs_set_resource_field`, `ecs_send_event`; `ecs_get_stats` (storage spec) is extended with the last `RunReport` per schedule. **Profiler tools** (built by #110 from the reflected `FrameTimings` and `AllocStats` of item 22; the editor profiler panel of SP8, #149, reads the same structs and the same names): `profiler_get_frame_timings` (the previous frame's `FrameTimings`, optional `name_prefix` filter) and `profiler_get_alloc_stats` (an `AllocStats` snapshot; empty with a typed `allocator_not_installed` error when the game did not install `CountingAllocator`). **2. Frame statistics (#63).** `exitium_profiler::stats` provides `StatsLayer` (a `tracing_subscriber::Layer`) and `FrameTimings`. The type is named `FrameTimings`, not `FrameStats`, because `exitium_app` already owns a `FrameStats` (frame count, delta). **All fields are reflectable in v1** (reflect-model: no `Duration`, no borrowed fields, no `ThreadId`), so item 22 can derive `Reflect` on them unchanged:

```rust
pub struct FrameTimings { pub frame: u64, pub total_ns: u64, pub spans: Vec<SpanTiming> }       // the previous frame's aggregate
pub struct SpanTiming   { pub name: String, pub label: Option<String>, pub thread: u32 /* thread index, rule below */,
                          pub calls: u32, pub total_ns: u64, pub max_ns: u64 }
pub struct AllocStats   { pub allocs: u64, pub deallocs: u64, pub live_bytes: u64, pub peak_bytes: u64 }
```

`FrameTimings::last() -> Arc<FrameTimings>` reads the previous frame (one `Mutex<Arc<_>>` swapped once per frame, so a reader never blocks a span).

*Thread index source.* `exitium_profiler` is a leaf crate and cannot see `exitium_tasks` (the only edge is `tasks -> profiler`), so it cannot ask the pool which worker it is. The index is derived inside the profiler, once per thread, from the **thread name**: a thread named `exitium-worker-N` (the name `TaskPool` gives its workers, tasks spec) with `N < 255` gets index `N + 1`; the first other thread that records a span gets **0** (in a game, the main thread, which calls `init`; in a test binary, whichever thread records first); every further unnamed or differently named thread gets `256, 257, ...` in first-seen order. `testing::capture` uses the **same mapping**, so "a worker's index" means the same in the ECS span test and in `FrameTimings`. A thread is classified on its first span and keeps its index for the process.

*Aggregation structure.* Each thread owns a small buffer (`Mutex<ThreadBuf>`, registered once in a global `Vec<Arc<_>>`) holding a `Vec<SpanAcc>` keyed by `(&'static str name, label id)`. A span close takes its own thread's lock (uncontended, about 15 ns) and updates one accumulator; no map and no allocation after the first sight of a pair. Labels are interned once into a `Vec<Box<str>>`. `end_frame` (called by `mark_frame`) locks each registered buffer once in turn, merges into the new `FrameTimings`, resets the accumulators and swaps the `Arc`. The layer records only spans whose name starts with a registered prefix (`exitium_ecs::`, `exitium_tasks::`, `exitium_render::` ...), so a frame's work is bounded.

*Budget (roadmap): frame stats at most 0.05 ms per frame.* Concretely: a recorded span costs <= 50 ns on close, and `end_frame` costs <= 20 us for 16 threads and 300 recorded spans, so the layer costs <= 35 us per frame at 300 spans (the reference scene's system, segment and job spans), under 0.05 ms. The bench in #63 asserts both numbers. With `profiling` off the layer does not exist: **zero cost**, the spans compile out. The MCP profiler tools (see "MCP / editor surface") read `FrameTimings::last()`; no stats code lives in `exitium_ecs`.

**3. Counting allocator (#64).** `exitium_profiler::alloc::CountingAllocator` is a `GlobalAlloc` wrapper over `std::alloc::System`. It is the crate's one designated `unsafe` module (`#![allow(unsafe_code)]` on `alloc.rs` only; every `unsafe` block has a `// SAFETY:` argument: the wrapper forwards the caller's `Layout` and pointer to `System` unchanged, so every `GlobalAlloc` contract is inherited). It has **Miri tests** (alloc, realloc grow and shrink, zero-size, over-aligned, dealloc balance) that run in the existing xtask Miri step, which finds the crate by grepping for `allow(unsafe_code)`; the allocator is **not** feature-gated, so the step always sees it. It is installed by the binary (`#[global_allocator]`) in games that want it and by benches that assert allocation counts; the engine never installs it itself, so a build that does not install it pays nothing (**zero cost when off**). High-risk: new `unsafe`.

*Budget (roadmap): at most 20 ns added per allocation.* Three global `AtomicU64`s plus a peak `fetch_max` would bounce one cache line between 4 threads (10 to 60 ns per contended `fetch_add`), so the counters are **sharded**:

- 16 shards, each `#[repr(align(64))]` and holding `allocs`, `deallocs` and `live_bytes` as `AtomicU64`, plus `last_checked` (below). **`live_bytes` is a signed quantity stored as two's-complement:** a shard's value is the bytes its own thread allocated minus the bytes its own thread freed, so a block allocated on thread A and freed on thread B makes B's shard **negative** (its `u64` wraps). Every comparison and the sum therefore treat the value as `i64` (wrapping add of deltas, summed as a wrapping `i64`); only the final total is clamped (`max(sum, 0) as u64`). A thread picks its shard once, from a `const`-initialised `thread_local! { static SHARD: Cell<u8> }` (no lazy allocation and no destructor, so it is safe to use inside `GlobalAlloc`; the first call assigns round-robin from a static counter, so more than 16 threads share a shard, with bounded contention).
- The hot path is two `Relaxed` `fetch_add`s on the thread's own line, one `last_checked` compare, and one thread-local read: about 3 to 6 ns uncontended and well under 20 ns with 4 threads, each on its own shard. The bench in #64 asserts <= 20 ns per allocation at 1 and at 4 threads.
- **Peak** is not a per-allocation `fetch_max`. Each shard keeps `last_checked: AtomicI64` (the shard's own cache line; with at most 16 allocating threads each shard has one writer, so plain relaxed loads and stores suffice). The rule, on **every** allocation and deallocation:
  - after an allocation: if `live as i64 - last_checked > 64 KiB`, sum all shards (16 relaxed loads), `fetch_max` the global peak with `max(sum, 0)`, and set `last_checked = live`;
  - after a deallocation: `last_checked = min(last_checked, live)` (a store to the thread's own line, only when `live < last_checked`).
  The ratchet keeps `last_checked <= live` at all times, so **a shard that frees and then allocates again measures its growth from its low point, not from its old high point** (a plain "only ever rises" `last_checked` misses this: shard A allocates 100 MB, checks, frees, then shard B allocates and checks, then A allocates 100 MB again with zero measured growth, so the true 200 MB would never be recorded; with the ratchet A's `last_checked` fell to 0 on the free and the re-allocation triggers a check). **Bound:** after any allocation a shard is at most 64 KiB above its `last_checked`, and `last_checked` is never above the shard's value at **any** moment since that shard's latest own check (the ratchet takes the minimum over that span; a shard that never checked counts as checked at 0 when the process started). At the true peak `T`, take `t*` = the latest check by any shard before `T`; every shard's own latest check is at or before `t*`, so every shard is at most 64 KiB above its value at `t*`, and the recorded sum at `t*` is within **16 x 64 KiB = 1 MiB** of the true peak (0.1% of the 1.1 GB memory budget it is used for). The 16 loads of one check are not an atomic snapshot, so the test allows a 2 MiB tolerance. The bound is stated for at most 16 allocating threads (one writer per shard); beyond that a shard is shared and the term becomes 64 KiB per thread sharing it. `peak_bytes` is a **lower bound** with this accuracy, documented on the field. Counts and `live_bytes` are exact when read (`live_bytes` is the clamped signed sum).
- `AllocStats::snapshot()` sums the shards (a few hundred ns, never on a hot path), and `AllocStats::reset_peak()` resets the peak. The editor's memory panel and `ecs_get_stats` (memory, storage spec) read them.

**4. `profile_scope!` field form (item 1) and the `testing` helper.** `profile_scope!("name", key = expr, ...)` records fields when `profiling` is on and expands to nothing when off (the literal-only form is unchanged). `exitium_profiler::testing` (compiled only with `profiling`) provides `capture(|| ...) -> CapturedSpans`. A `tracing` subscriber set with `set_default` is **thread-local**, so a closure-scoped subscriber would miss every span on a worker thread. `capture` therefore installs, once per process, a **global** dispatcher (`tracing::subscriber::set_global_default`, in a `OnceLock`) that forwards every span on every thread into a registered sink, and takes a process-wide `Mutex` for the duration of the closure so concurrent capture tests serialize (a `testing::serial` guard documents the rule). It records `(name, fields, thread index, parent name)` per span, with the thread index from the **same mapping as `FrameTimings`** (thread name `exitium-worker-N` gives `N + 1`, see "Thread index source" under item 2). `CapturedSpans` has `names()`, `with_field(name, key)`, `threads_of(name)` and `parent_of(name)` accessors.

`exitium_profiler` also exports a small **span-handle API** so that `exitium_tasks` can hold and re-enter a span without a `tracing` dependency of its own (`tasks` has no third-party dependency, tasks spec): `SpanHandle` (under `profiling` a cloneable `Send + Sync` wrapper of a `tracing::Span`; with `profiling` off a zero-size type whose methods are empty, so it costs nothing), `profile_span!("name", key = expr, ..) -> SpanHandle` (creates a span as a child of the current one and does **not** enter it), `SpanHandle::enter(&self) -> impl Drop` (a guard that makes it current on this thread) and `SpanHandle::record(&self, key, value)` (fills a field declared up front, used for `jobs` at scope end). Delivered by item 1. It exists so the ECS and tasks span tests need **no** direct `tracing` dev-dependency and do not depend on `StatsLayer`. It must not be combined with `init()`'s global registry in one process (a test binary never calls `init`).

**5. Executor and job spans (#65), with the `tasks -> profiler` edge.** #65 is the tail issue (roadmap: it runs alone after the ECS lane, and its Footprint is `exitium_ecs`, `exitium_tasks`, `exitium_profiler`). It:

- adds the workspace edge `exitium_tasks -> exitium_profiler` (not in intake 1) and `exitium_tasks` gets `[features] profiling = ["exitium_profiler/profiling"]`, **off by default**; it extends `exitium_ecs`'s feature to `profiling = ["exitium_profiler/profiling", "exitium_tasks/profiling"]`; it adds `("exitium_tasks", "profiling")` to xtask's `FEATURE_CHECKS` (the xtask hotspot, so #65 runs alone, never beside #66);
- adds the tasks spans: `exitium_tasks::scope` (field `jobs`: the number of jobs spawned, recorded at scope end) and `exitium_tasks::parallel_for` (fields `len`, `batch`), and a per-job span `exitium_tasks::job` **only** under `profiling`, which costs one `tracing` span per job (acceptable only with `profiling`; the tasks spec's benchmark rows are measured with it off);
- **specifies explicit span propagation into jobs, from the scope's own span.** `tracing`'s current span is thread-local: a job that runs on a worker does not inherit the span of the thread that spawned it, so "nested under the segment span" does not happen by itself. Under `profiling`:
  1. `scope()` creates its `exitium_tasks::scope` span on entry (a child of whatever is current on the calling thread, which for the ECS is the `segment` span) with `profile_span!`, and **stores the `SpanHandle` in `ScopeShared`** (tasks spec; one extra field behind `profiling`).
  2. **Every `Scope::spawn` propagates the scope's stored span, never `Span::current()`**, including a `spawn` made from inside a running job (the parallel executor spawns a successor from inside its predecessor's job). The wrapper clones the handle (one `Arc` clone), and the job wrapper enters it, then opens the per-job `exitium_tasks::job` span inside it and runs `f` inside that.
  3. The chain is therefore **`segment -> exitium_tasks::scope -> exitium_tasks::job -> system`**, and all job spans of one scope are **siblings**. Propagating `Span::current()` instead would make a successor's job a child of its predecessor's job span, nested as deep as the longest dependency chain, and a system span's parent would be the wrong job. A nested `scope()` opened inside a system (`par_iter_mut`) is a child of that system's span, because it reads `Span::current()` on its own thread, not on the spawner's.
  With `profiling` off the wrapper is unchanged and `SpanHandle` is zero-size, so nothing is cloned or entered;
- adds the ECS spans of item 17 (this spec's "Profiling hooks") and the span test, which uses the **global** `testing::capture` above and asserts the parent chain `exitium_ecs::schedule::segment -> exitium_tasks::scope -> exitium_tasks::job -> exitium_ecs::schedule::system`, and that no `exitium_tasks::job` span has another job span as its parent (a chain of dependent systems does not deepen the job spans).

The `ecs -> profiler` edge is in intake 1, so the ECS span code compiles in item 17's issue; the tasks half arrives with #65 in the same issue. ## Test plan

- **Conflict rule:** a matrix of read/read (no conflict), read/write, write/write, `Changed<A>` reader versus `A` writer (conflict), resource read/write combinations, exclusive versus anything, and filter-disjoint pairs (`With<X>` against `Without<X>` do not conflict; `Option<&T>` adds no `with`); the same matrix inside one system (`ParamConflict`); `Query<(&A, &mut A)>` reported by the storage layer.
- **Graph:** `before`/`after`/sets/`chain` ordering respected in the plan; a set with no members is a no-op; cycle error names the systems; `UnknownSystem` and `DuplicateSystem`; node order equals registration order when unconstrained; **sync-point position is pinned** (`SyncPoint(k)` sits immediately before its first-registered successor, `SyncPoint(end)` is last, unrelated systems registered before that successor run before the sync point); sync-point levels (A `Commands` system, B after A: sync between; unrelated deferred systems share one sync point; final sync always present); a conflicting unordered pair is serialized and reported as an ambiguity, `Deny` makes build fail, an explicitly ordered conflicting pair is not reported; adding a system after the first build keeps existing `last_run`s.
- **Commands:** spawn-then-insert on the reserved id within one buffer; despawn of a reserved entity; ordering across two buffers in plan order; commands on a dead entity are skipped and counted; `spawn_batch`; closure command; the buffer never applies mid-run (a later system in the same segment does not see it unless ordered after); no buffer survives the end of a run; a panic abandons every queue: reserved-but-unexecuted spawn ids are flushed and despawned, so a following sync node finds **no** component-less phantom entity (`Query<Entity>` count and `WorldStats` unchanged), while a spawn that already ran is kept.
- **Tick contract (end to end, from the storage spec's hand-offs):** a system that writes through `Query::get_mut` does not see that write as `Changed` on its next run, while an exclusive world-level write is seen; apply a command buffer after system S, run S again, S sees the command's changes exactly once; `(&mut A, Changed<A>)` does not retrigger itself; first run sees everything; a system idle for more than 2^30 ticks (force the counter) sees everything once; sweep polling: a schedule run with `needs_tick_check()` advances the sweep by one slice per sync node, a full sweep completes across runs, and no stored age exceeds the bound (reuses the storage spec's `force_change_tick` hooks).

1. **Cursor `last_run`: resolved in this PR.** Per-system `last_run` is a 64-bit `ChangeCursor`, resolved by age on every run, so nothing is clamped. `ecs-storage-queries.md` is amended in this PR ("Where `last_run` lives", the sweep's `last_run` bullet and the #22 hand-off) so the two specs agree. Residual question: confirm the one `resolve_cursor` per system run (two compares) is acceptable against the 120 ns dispatch budget.
2. **Labels and sets as `&'static str` newtypes** (readable, MCP-friendly, collision risk handled by the `crate::name` convention) versus type-based labels. Confirm?
3. **Sync-point rule.** Deferred buffers apply only at sync points that exist because of an explicit ordering edge, plus at the end of a run, in both executors. The alternative (apply after every system on one thread) is friendlier but makes single-threaded and parallel behave differently. Confirm the strict rule?
4. **Event clocks.** `Frame` and `Fixed` are an ECS concept here; the app spec must call `update_events` for both. If the app wants a single clock, drop `EventClock`.
5. **Non-send resources: resolved in this PR.** Non-send resources, main-thread systems and script systems are in the MVP (owner decision 2026-11-24): `NonSend`/`NonSendMut`, an owner-thread `NonSendSlot` (designated #6), a `main_thread` flag that makes the system a barrier, and `exclusive(name, f)` for script systems. This also covers wgpu handles that are `!Send` on wasm32. The render spec chooses which of its resources are non-send.
6. **Run conditions and states.** Cut from v1; state gating is by schedule label. Does Glutton's UI flow need `run_if`?
7. **Per-system entity reservation cache.** Needs an `Entities` API to take unused reservations back (storage spec). Only worth it if the `spawn` round-trip budget is missed.
8. **`Box<dyn Command>` per command** versus a byte arena. The box is simple and safe; an arena would need a new designated unsafe module. Perf follow-up if the 60 ns record budget is missed.
9. **Ambiguity default.** `Report` (data only) versus warning at build in debug builds (needs a logging path the ECS does not have). The app could print `ScheduleReport::ambiguities`.
10. **System enable/disable and removal at runtime** (an editor "pause system" feature) is deferred; it would need a tool and a command when added.
11. **Absolute budgets** are provisional; the `perf` agent confirms them after items 18 and 21 on the reference runner and on the 4-thread min-spec profile (#66). The binding numbers are the ratios (>= 3.0x at 4 threads, <= 1.1x for a chain); the 40 ms ceiling of the 1M-entity parallel tick is the first number to re-baseline.
12. **Which schedules run `ExecutorKind::Parallel`?** The ECS default stays `SingleThreaded` (the safe, repeatable choice for tests and tools). Recommendation for the app spec: `exitium_app` sets `Parallel` on the frame `Update` schedule when `TaskPool` reports more than one thread, keeps `Fixed` (simulation steps that must be repeatable for netcode and replays) on `SingleThreaded` **and its systems free of `par_iter_mut`, or the process on a single-thread default pool**, because `SingleThreaded` alone does not stop nested parallel iteration (see "Determinism"), until determinism of the parallel executor is specified, and leaves `Startup` single-threaded. The facade's `ThreadingPlugin` (not `exitium_app`) installs the pool with `TaskPool::set_default`. The app spec (app-platform, "Executors and the thread pool") owns which schedules are `Parallel`; this crate keeps `SingleThreaded` as its default.
13. **One Luau state per worker** (parallel script systems) is an extension, not v1: scripts run as exclusive systems on the calling thread. Revisit when a profile shows script time on the critical path.
14. **Rejected: a thread-local store instead of designated #6.** A safe alternative keeps non-send values in a `thread_local!` `RefCell<HashMap<(WorldId, ResourceId), Box<dyn Any>>>` on the owner thread, with the `World` holding only a token. Rejected: (a) the API would be closure-only (`with_non_send(|v| ..)`), so `NonSend<'w, T>` could not hand out a borrow that lives for the system run, and `non_send_resource_scope` would double-borrow the `RefCell`; (b) every access pays a TLS lookup plus a hash probe, against a slot index plus one thread-id compare; (c) two `World`s on one thread (tests, a headless server beside an editor) must be keyed by `WorldId`, and values would be dropped at thread exit instead of at world drop, which breaks destructor order; (d) `Commands::insert_non_send_resource` and the access sets would still need the id space. If review prefers no new `unsafe`, this is the fallback, at the cost of `NonSendMut` being closure-shaped.
